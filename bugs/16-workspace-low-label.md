# 16 · 工作区被打上 Low 完整性标签（合法项目目录被当成沙箱内部）

- **状态**：已确认（DSH 官方确认为有意设计）
- **类型**：DSH 引起
- **发现**：2026-11-21 · dsh-doctor v0.14.12 起可检出并修复

## 症状

工作区目录的权限看起来完全正常，但：

- 在 DSH 会话里编译出的 exe 一运行就写不了文件（配置、日志、输出全失败）；
- 安装器（NSIS 等）往项目目录展开时报拒绝访问；
- 从资源管理器把文件拖出该目录时弹安全警告（Windows 把它视为不可信位置）。

## 根因

DSH 的沙箱设计意图：降低沙箱内子进程的完整性级别，再用能力 SID 限制写权限，从而拦截写入。它把工作区目录本身标为 Low，作为"向下写"的隔离手段。

但工作区就是用户自己的项目目录——缓存的前提是"这个目录是沙箱内部"，它的效果却活过了这个前提，作用到了无关的文件上。目录被打上：

```
S-1-4-xxx:(OI)(CI)(W,D,DC)        能力 ACE
Mandatory Label\Low:(OI)(CI)(NW)  低完整性标签
```

目录里的程序继承 Low → 它们的所有写入都是"向上写" → 全部被拒。

上游 discussion 里至少四份报告：

| 时间 | 报告 | 表现 |
|---|---|---|
| 2026-09 | #7709 | 低完整性标签悄悄破坏用户自己的工具链启动 |
| 2026-10 | #9314 | 工作区里编译的 exe 以低完整性运行，所有写入失败 |
| 2026-10 | #9559 | 标签没传到已有子目录，子目录写入被拒 |
| 2026-10-19 | #10270 | 下载文件夹当工作区，NSIS 安装器直接报错 |

官方回应是"有意设计"：工作区的权限修改是常驻的、跨会话复用的缓存，dispose 时故意不撤销（否则下次要重新递归整棵树）。维护者同时承认："真正没有想清楚的是影响范围。"

## 为什么写探针探不出来

Medium 完整性进程对 Low 对象的写入是**放行**的（完整性模型只拦向上写）。所以 `workspace-not-writable` 的真写探针在这里永远是绿的——必须读 SDDL 看标签。

## 修法

```powershell
icacls "<工作区目录>" /setintegritylevel '(OI)(CI)Medium'
icacls "<工作区目录>" /remove:d '*S-1-1-0'
```

能力 ACE 不动（沙箱写入靠它）。`dsh-doctor fix -Id workspace-label`（v0.14.12）先备份、改完复检（读不回 SDDL = 失败，fail-closed）。

## 防复发

官方明确这是有意设计且缓存跨会话复用——DSH 每次给工作区供给权限都可能重新盖章。选择：

1. 换工作区到沙箱外的普通目录（推荐）；
2. 接受现状，每次供给后跑一次体检，医生自动拉回 Medium；
3. 反复复发且工作区本来就在危险位置（桌面/下载）时，直接 `workspace-entry` 移出注册表。

## 验证方式

`tests/workspace-label.test.mjs`：假引擎喂 Low/Medium/拒绝项三种 SDDL，断言 finding id、严重度、fixId 接线与 fail-closed 复检行为。
